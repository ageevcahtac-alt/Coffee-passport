## Итог в одном абзаце

Аудит Codex **качественный и в основном точный**: все ключевые технические факты подтвердились по коду, Codex честно отделил FACT от RISK и не подменял тесты предположениями. Основные расхождения — в **приоритизации и масштабе решений**: (1) P0-02 недооценён — на текущем Render-деплое любой посетитель одним кликом получает роль `cafe_admin` реальной пилотной кофейни и вместе с ней чтение всех дегустаций гостей этой точки; (2) ряд UX-пунктов (главная, «простой путь» формы, outbox) Codex формулирует шире, чем нужно до пилота, где гость приходит по QR, а не с главной; (3) пропущены несколько дешёвых, но заметных гостю проблем: `html lang="en"` (автоперевод Chrome на Android), постоянная плавающая Dev-панель над гостевым интерфейсом, stale-closure в `/scan`, который обнуляет прошлый фикс синхронизации каталога, и порядок отключения demo-ролей (demo-аккаунты привязаны к *реальным* `shop-xo-vsevolozhsk` / `roaster-xo`).

## CONFIRMED — Codex прав

### C-1. P0-01 — admin API защищён только middleware на уязвимой версии Next.js
- Проверено: `next: "14.2.0"` в `package.json` и lockfile. `middleware.ts` — единственная проверка Basic Auth для `/admin` и `/api/admin/**`. `GET /api/admin/partner-requests` читает **все** заявки партнёров через service-role клиент без собственной проверки.
- Дополнение к Codex: `PATCH /api/admin/partner-requests/[id]` тоже защищён только middleware — это не только чтение, но и изменение заявок.
- Дополнение к Codex: Render — тоже self-hosted Node (`render.yaml`, `npm start`), поэтому риск относится к **текущему живому деплою**, а не только к будущему Timeweb.
- Решение Codex (обновить Next + проверка внутри handler) правильное и минимальное. Уточнение: обновляться в пределах **последнего патча линии 14.2.x**, а не на 15.x. Мажорный апгрейд — это ненужный redesign перед пилотом: async `params`/`cookies`, React 19.

### C-2. P0-02 — DB demo-role путь включён (Codex недооценил масштаб)
Факты подтверждены: `0029` вставляет `pilot_demo_enabled=true`; `dev_seed_staff_profile()` — `security definer`, `grant execute ... to authenticated`; `render.yaml` задаёт `NEXT_PUBLIC_PILOT_DEMO_ENABLED="true"`; общий demo-пароль захардкожен в `lib/auth/pilotStaff.ts` (в git; в клиентский бандл не попадает — проверено поиском по `.next/static`; demo-email попадают).

Чего Codex не связал:
1. **На текущем Render-сайте эксплуатация не требует пароля.** `DevRoleSwitcher` рендерится в root layout для каждого посетителя. При включённом флаге он показывает кнопки «Кофейня / Обжарщик / Бариста / Фидбек», которые вызывают `signInAsPilotStaff`. Один клик — и сессия `cafe@test.com` с ролью `cafe_admin`.
2. **Demo-роли привязаны к реальным пилотным сущностям**: `cafe_id = 'shop-xo-vsevolozhsk'` и `roaster_id = 'roaster-xo'`. Это не песочница, а реальная кофейня и обжарщик пилота.
3. **Утечка данных гостей.** Политика `"shop staff read own shop checkins"` (`0007`) даёт `cafe_admin`/`barista` полный `select` по `checkins` своей точки: заметки, `liked/disliked`, оценки бариста, `owner_user_id`. Любой посетитель может стать `cafe_admin` пилотной кофейни, поэтому **все дегустации реальных гостей этой кофейни фактически доступны анониму**. Ради этого P0 нужно закрыть до гостей, а не «до расширения».
4. Даже без UI-флага: если demo-аккаунты ещё не созданы в проекте, а «Confirm email» выключен (код прямо требует его выключить для demo), любой может зарегистрировать `admin@test.com` через публичный anon key и вызвать RPC.

**Важный операционный нюанс, которого нет у Codex.** Если реальные сотрудники XO сейчас работают через demo-аккаунты, простое выключение флага отрежет им доступ. Правильный порядок:
1. Создать реальных staff-пользователей (личные email и пароли).
2. Вручную назначить им `profiles.role/cafe_id/roaster_id/barista_id`.
3. Только после этого `pilot_demo_enabled=false` и `NEXT_PUBLIC_PILOT_DEMO_ENABLED` убрать/`false` с пересборкой: это build-time переменная.
4. Сменить пароли четырёх `*@test.com` или удалить их, понизить их `profiles.role` до `enthusiast`.

### C-3. P1-03 — «Назад» из шага бариста сбрасывает оценку
Подтверждено: `pendingTasteValues` хранится в странице, но `<TastingForm>` монтируется заново без initial-значений. Все `useState` внутри формы стартуют с `0`/`3`/`''`. Гость теряет всё, что ввёл. Фикс локальный: передать `initialValues` в `TastingForm`.

### C-4. P1-04 — `/journey` и `ScanLotModal` не загружают каталог лотов
Подтверждено: `syncLotsFromSupabase` вызывается только в `/passport/[lotId]`, `/scan`, `XoStoreImportNotice` и staff-страницах. `/journey` его не вызывает, `useLots` только подписывается на store. `CoffeeJourney` делает `if (!lot) return null` в двух местах. Реальные лоты живут в Supabase (канонический слой, XO-мост), а не в seed, поэтому на новом устройстве история и карта показываются частично. `ScanLotModal` захардкожен на `shop-xo-vsevolozhsk`; для пилота одной кофейни это приемлемо, но должно быть осознанным.

### C-5. P2-02 — «Любимая обработка» и «регион»
Подтверждено: `computeFavoriteProcesses` и `computeFavoriteRegions` считают частоту по всем записям без учёта оценки, а «регион» — это `country`. P2, после пилота; если трогать, то сначала переименовать подписи («Чаще всего пили»), а не строить рекомендательную систему.

### C-6. P2-05 — `FarmerPinningModal` без ограничения высоты
Подтверждено: `fixed inset-0 flex items-center justify-center p-6`, `body.overflow = hidden`, у контента нет `max-h`/`overflow-y-auto`. У анонимного варианта самый длинный контент. Фикс — пара Tailwind-классов, поэтому включён в shortlist.

### C-7. Прочие подтверждённые наблюдения
- Новые checkins сохраняются с `isPublic: false`, community view работает по согласию. Codex прав, это не трогать.
- `createAdminSupabaseClient` использует service-role, комментарий в `/api/barista/[id]` про anon key устарел.
- Cron-routes закрыты секретом. Security-definer RPC `events_ingest_candidate` / `events_archive_expired` / `cafe_menu_expire_discontinuing` выданы `anon`. Ingest пишет только `pending_review`, так что это спам-риск, а не эскалация (P2/P3).
- Lint не настроен (интерактивный `next lint`). P3, к пилоту отношения не имеет.
- P2-01, P2-03, P2-06, P2-07, P3-01…P3-04 — согласен с формулировкой и приоритетом. Ссылка «Меню кофейни» в `/dashboard/barista` ведёт в layout, где требуется `cafe_admin` (`requireStaffRole` проверяет строгое равенство роли); бариста получит редирект.
- Список «Что уже работает хорошо» — согласен полностью. Особенно важно не трогать независимость первого впечатления, канонический слой и immutable roast batches.

## PARTIALLY CONFIRMED — проблема есть, но причина/масштаб/решение неточны

### PC-1. P1-01 — главная и пустой `/journey`
Факты верны (`app/(site)/page.tsx`: «Платформа для Specialty Coffee сообщества», «Фиксирует дескрипторы…»). Но **для пилота гость приходит по QR сразу в `/passport/[lotId]`**, главную он почти не видит. Поэтому главная — P2, после пилота. Пустой `/journey` важнее, потому что туда ведёт модалка после сохранения. Но и тут достаточно одной-двух строк текста. Новые экраны и «пример будущей записи» не нужны.

### PC-2. P1-02 — молоко и перегруженная форма
- **Молоко — подтверждаю как реальный P1-блокер.** `isDrinkSelectionComplete` для `cow` требует и `cowMilkType` («Цельное» / «Нормализованное по жиру»), и `fatContentPercent !== null`. Варианта «Не знаю» нет, и гость, заказавший латте, не может пройти дальше, пока не угадает. Самый дешёвый и важный фикс shortlist.
- **«Простой путь вместо формы» — отклоняю как pre-pilot работу.** Обязательна по факту только общая оценка (`canSave = rating > 0`), всё остальное уже опционально. Перестройка иерархии формы — редизайн, который лучше делать по данным пилота. До пилота достаточно явной подписи «необязательно» у блоков детализации.
- **Слайдеры по умолчанию 3, которые записываются как наблюдение — подтверждаю, но после пилота.** Чтобы отличать «не оценивал» от «3», нужны nullable-значения через `TastingRecord` → `recordToRow` → агрегаты. Это межслойное изменение с риском регрессий, и пилоту оно не мешает.

### PC-3. P1-05 — облачное сохранение и claim
Факты подтверждены. `addTastingRecord` пишет локально, insert в Supabase fire-and-forget, ошибка уходит только в `console.warn`. `claimAnonymousTastings` перепривязывает записи локально до insert, при ошибке повторной попытки нет. `purgeRecordsForUser` при смене аккаунта удаляет локальные записи, в том числе не доехавшие до облака.

Но **решение Codex (outbox, видимые статусы, гарантированная повторная отправка) избыточно для пилота.** Минимальный фикс, закрывающий все три пути: в `syncCheckinsForUser` после pull загрузить в Supabase локальные записи этого `userId`, которых нет в ответе (`upsert` по `id` с `ignoreDuplicates`). `syncCheckinsForUser` и так вызывается при каждой загрузке `currentUser`, так что это и есть «retry» без новой инфраструктуры. В `userScope` перед purge стоит не удалять записи, которые не подтверждены сервером, либо сначала дождаться sync.

Local-only каппинги (`cuppingsStore`) — согласен с Codex, что это отдельный журнал. До пилота **не переносить в облако**, просто не обещать сохранность в аккаунте.

### PC-4. P1-06 — ошибки входа, подтверждение, восстановление пароля
- **Error-redirect — подтверждаю, P1.** `login/page.tsx` формирует `errorRedirect = '/auth/login?next=...'`, `actions.ts` дописывает `?error=...`, и получается `?next=/passport/X?error=...`. `searchParams.error` пуст, и гость с неверным паролем **не видит никакой ошибки**. Фикс: склеивать через `URL`/`URLSearchParams`. Попутно пропускать `errorRedirect` через `safeNextPath`. Open redirect через подделанную форму server action маловероятен (Next проверяет Origin), но фикс бесплатный.
- **`data.session` при signup — условный риск, не текущий баг.** Код demo-флоу прямо требует выключенного «Confirm email», так что в текущем проекте сессия, скорее всего, выдаётся сразу. Нужна операционная проверка настройки на целевом проекте, а не правка кода. Если подтверждение включат, понадобится экран «Проверьте почту».
- **Восстановление пароля — P2.** Codex прав, что его нет: в коде нет ни `resetPasswordForEmail`, ни `updateUser`. Но это новая функция, требующая SMTP в Supabase. Для пилота с десятками гостей достаточно ручного сброса через Supabase dashboard по запросу.

### PC-5. P1-07 — unpublished рецепты бариста
Подтверждено: service-role, нет `.eq('is_public', true)`. Но это параметры заваривания, а не персональные данные, и собственный UI этот route не использует. Реальный приоритет — P2. Фикс в одну строку, поэтому он всё равно в shortlist как попутный.

### PC-6. P2-04 — сканер `/scan` (Codex недооценил)
Codex правильно увидел, что «обработчик может использовать первоначальный каталог», но не сделал вывод. `QrScanner` ставит effect с `[]` и вызывает `onDecode` из **первого рендера**. `resolveAndNavigate` в `/scan` замыкает `lots` начального снапшота, то есть seed и localStorage, до завершения `syncLotsFromSupabase`. Поэтому **реальный канонический лот в `/scan` всегда даёт «Лот не найден»**, а сканер после этого останавливается (`decodedRef = true`). Прошлый фикс (добавленный sync, см. комментарий в `scan/page.tsx`) этим фактически нейтрализован. На `/scan` ведёт ссылка из `CoffeeJourney`, так что это P1, хотя основной QR через камеру телефона работает.

Минимальный фикс без новой платформы: в `/scan` и `ScanLotModal` не валидировать лот по локальному кэшу, а сразу переходить на `/passport/{lotId}`. Паспорт сам синхронизирует каталог и корректно показывает неизвестный лот. Для `ScanLotModal` проверку меню можно оставить, но после `await syncLotsFromSupabase()`.

### PC-7. P2-08 — legacy broad reads
Политики `0004` действительно дают `authenticated` чтение `reviews`/`user_taste_profiles`/`review_replies`. Но поиск по `app/components/lib` не нашёл ни одного обращения к этим таблицам, поэтому они, вероятно, пусты. Это P3-гигиена: отозвать политики одной миграцией, когда будет удобно. До пилота не нужно, если таблицы пусты; это стоит проверить одним `count(*)`.

Публичная проекция коммерческих полей green lot (договоры, закупка) — реальный вопрос, но Codex сам не нашёл заполненных данных. P2: проверить, заполняются ли эти поля в `roaster-xo`.

### PC-8. P2-09 — bootstrap миграций с нуля
Верно, что цепочка миграций не гарантирует чистый bootstrap. Но перенос на Timeweb касается **хостинга Next.js-приложения**, а Supabase остаётся тем же облачным проектом. Bootstrap не нужен и в shortlist не входит. Если когда-нибудь понадобится новая БД — это отдельный проект.

### PC-9. P2-10 — accessibility (недооценён `lang`)
`<html lang="en">` при русском интерфейсе — не только вопрос скринридеров. **Chrome на Android предлагает гостю «перевести страницу с английского»**, а при включённом автопереводе искажает русский текст. Гость видит это в первые секунды после QR. Фикс — одно слово (`lang="ru"`), поэтому он в shortlist. Связь label/range у `FlavorSlider` и focus trap — P2 после пилота.

### PC-10. P2-11 — DevRoleSwitcher в production (недооценён)
`DevRoleSwitcher` рендерится **всегда, для каждого гостя**, развёрнутым по умолчанию. Это `fixed bottom-… z-40` панель с подписью «Dev» и кнопками «Энтузиаст» и «Админ» (кнопка «Админ» ведёт на `/admin` и вызывает браузерный Basic Auth prompt). - В `syncCheckinsForUser(userId, true)` после успешного pull найти локальные записи с `record.userId === userId`, чьих `id` нет среди полученных строк, и отправить их одним `upsert(rows, { onConflict: 'id', ignoreDuplicates: true })`. Ошибка — `console.warn`, локальные данные не трогать. Это заменяет отдельную retry-логику для `addTastingRecord` и `claimAnonymousTastings`.
- `lib/journey/userScope.ts`: перед `purgeRecordsForUser(previousUserId)` не удалять записи предыдущего пользователя, которые не подтверждены сервером. Достаточно, если purge выполняется только после успешного sync предыдущего пользователя, либо записи остаются в изолированном виде, недоступном текущему пользователю. Выбрать самый простой вариант, не ломающий существующие тесты изоляции. Если безопасного простого варианта нет — оставить purge как есть и описать это в отчёте; основное покрытие даёт upsert.
- **Не** добавлять outbox, очереди, UI-статусы синхронизации, не трогать `cuppingsStore`.
- Тесты (с моком Supabase-клиента, как в существующих тестах store/claim): локальная запись без серверной копии → upsert вызывается с ней; запись уже на сервере → не дублируется; анонимный режим → upsert не вызывается.
