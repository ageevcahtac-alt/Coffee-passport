A / Executive Summary

Lot нужно расщепить на четыре сущности — и перестать путать «эталон» с «историей попыток»

  1. 1. Сегодняшний Lot уже незаметно смешивает происхождение кофе, физическую партию зерна и коммерческий продукт в один плоский объект. Это надо явно разделить на Coffee (происхождение) → Green Lot (партия зелёного) → Lot (коммерческий продукт).
  2. 2. Текущий тип RoastProfile в коде уже ведёт себя как история попыток обжарки (массив, сортировка по дате, показ всех записей), а не как единственный эталон — но не имеет флага, какая запись сейчас «эталонная». Это ровно тот же разрыв, что и запрошенный Reference Roast Profile vs. Roast Batch — его нужно формализовать, а не изобретать заново.
  3. 3. CONFLICT Reference Taste Profile (Lot.roasterFlavorProfile) сегодня — одно мутируемое поле без истории вообще. Это прямо нарушает принцип «история не переписывается задним числом» уже сейчас, при одном ростере и одном пилоте — не в будущем.
  4. 4. Один Green Lot может законно порождать несколько коммерческих Lot (например, один и тот же зелёный кофе — отдельным продуктом под фильтр и отдельным под эспрессо). Модель должна поддерживать это как обычный, не крайний случай.
  5. 5. generateLotId() сегодня проверяет уникальность только внутри одного браузера (localStorage) — при двух устройствах одного ростера коллизия ID физически возможна уже сейчас, до всякого мультиростерного будущего.
  6. 6. Source of truth должен переехать в Supabase — но не потому что «это очевидно», а потому что Lot уже используется как FK-цель (текстовая) в трёх реальных Supabase-таблицах (checkins, recipes, cafe_menu_entries), и продолжать держать источник истины вне БД, в которой уже живут его потребители, — единственный вариант, который гарантированно не масштабируется.
  7. 7. Миграция 0001 (lots/coffees/coffee_shop_lots) не является источником истины — она мертва — но её структура (разделение coffees=происхождение от lots=партия) независимо подтверждает правильность разделения Coffee/Lot, предложенного здесь. Использовать её напрямую всё равно нельзя: в ней нет Green Lot, Roast Batch, Reference Taste Profile и никакой связи с checkins/loyalty/barista.
  8. 8. Barista и Loyalty осознанно не получают прямой связи с Lot — оба уже корректно спроектированы вокруг Coffee Shop / Guest, добавление Lot FK туда решало бы проблему, которой не существует.
  9. 9. Инвентаризация количества («Low Stock», «Sold Out» как автоматически вычисляемые статусы) сознательно исключена из модели Lot — учёт остатков в проекте явно вне периметра продукта и передан внешним системам (Yumi/iiko), это не Stage 3 придумывает заново, это уже существующее продуктовое решение.
  10. 10. Итоговая рекомендация — одна: перевести Coffee/Green Lot/Lot/Roast Profile/Roast Batch/Reference Taste Profile в реальные таблицы Supabase, с неразрушающей, аддитивной стратегией миграции существующих текстовых связей (раздел I), без единого изменения текущего UI.

C / Target Lot Definition

Lot — коммерческий продукт, знающий свою партию и свой эталон, но не хранящий их данные внутри себя

Финальное определение: Lot — это коммерческая единица кофе: ссылка на одну конкретную физическую партию зелёного зерна (Green Lot) плюс один активный эталонный подход к её раскрытию (Reference Roast Profile) плюс один активный ожидаемый вкусовой профиль (Reference Taste Profile), под собственным публичным идентификатором, вокруг которого собираются реальные события (Roast Batch, Recipe, Tasting) — но ни одно из них не хранится как поле внутри самого Lot.

Lot ЕСТЬ

публичная идентичность продукта (id, отображаемое имя, дескрипторы, тип обжарки, статус жизненного цикла) + указатель на Green Lot + указатель на активный Reference Roast Profile + указатель на активный Reference Taste Profile.

Lot НЕ ЕСТЬ

ни сама партия зерна (это Green Lot), ни сама обжарка (это Roast Batch), ни сама дегустация (это Tasting), ни заказ, ни рецепт, ни отзыв, ни лояльность, ни пользователь любой роли — Lot их только связывает по FK.

G / Versioning

Версионировать ровно два поля — не событийный журнал, а неизменяемые снимки

Что версионируется: Reference Roast Profile и Reference Taste Profile. Что НЕ версионируется отдельно: сам Lot (описательные поля вроде имени/дескрипторов могут просто редактироваться на месте — они не участвуют в сравнении «что обещали vs что получилось»), Green Lot (одна физическая партия не меняется задним числом), Roast Batch (каждый батч — уже неизменяемое событие по своей природе, новое событие = новая строка, никогда не редактирование старой).

Reference Roast Profile

Каждое изменение подхода к обжарке — новая строка со статусом (draft/active/superseded) и effective_from. Ровно один active на Lot. Каждый Roast Batch хранит FK на ту версию, которой он фактически следовал — не на «текущую активную».

Reference Taste Profile

Тот же паттерн: новая версия при изменении 4-осевого эталона, статус active/superseded. Каждая Tasting-запись (checkins) при создании захватывает FK на версию, которая была active в момент дегустации — не на «текущую».

Почему этого достаточно и не нужен event sourcing: задача — не восстановить полную историю изменений мысли ростера, а гарантировать, что уже состоявшийся Roast Batch и уже состоявшаяся Tasting навсегда остаются привязаны к тому эталону, который был в момент события. Immutable versioned rows + захват FK в момент записи решают именно это, без журнала событий, диффов или отдельного audit-log-механизма.

CONFLICT, зафиксированный, не исправленный: сегодняшний Lot.roasterFlavorProfile — одно мутируемое поле без истории. Любой исторический checkins, созданный до миграции, физически не может «вспомнить», какой была roasterFlavorProfile в момент своей записи — это невосстановимая потеря, которую нужно явно принять при миграции (раздел L), а не пытаться реконструировать задним числом.

H / Lifecycle

Четыре статуса, не шесть — «Low Stock» и «Sold Out» не принадлежат Lot

СтатусЗначение
draftсоздан ростером, ещё не тестировался — не виден ни в одном каталоге
testingесть Roast Batch, эталонный профиль ещё не устоялся — виден только ростеру
activeэталон устоялся, доступен кофейням для добавления в меню
archivedснят с производства ростером — archived ≠ deleted (ниже)

Отклонено: «Low Stock» и «Sold Out» как статусы Lot. Причина двойная: (1) остаток физического товара — это уже свойство Green Lot (сколько кг закуплено/осталось), а не самого коммерческого продукта — Lot может быть «в наличии у Кофейни А» и «закончился у Кофейни Б» одновременно, что уже корректно решено на уровне cafe_menu_entries.status (new/active/discontinuing) для каждой кофейни отдельно; (2) в этом проекте явно зафиксировано ранее: учёт остатков/списание для лотов — вне периметра продукта, обслуживается внешними системами (Yumi/iiko), а не Coffee Passport. Добавление количественного статуса на сам Lot заново открывало бы вопрос, который уже был закрыт.

Archived ≠ Deleted: архивная запись Lot остаётся в БД со всеми связанными Green Lot / Roast Profile / Roast Batch / Recipe / Tasting нетронутыми и читаемыми. Единственный эффект архивации — Lot исчезает из списков «доступно для добавления в новое меню» и из discovery-поверхностей; гость с существующей дегустацией по-прежнему открывает свой Passport по старой ссылке без ошибок.

J / localStorage → Supabase

Переезжает в Supabase

Coffee (происхождение), Green Lot, Lot (сам объект), Reference Roast Profile (версии), Roast Batch (события), Reference Taste Profile (версии). Всё это сегодня — coffee-passport:lots и coffee-passport:roast-profiles в localStorage.

Остаётся client-side

Черновики формы до сохранения (обычное UI-состояние), любые UI-предпочтения отображения (сортировка, развёрнутые вкладки). Ничего из данных, формирующих идентичность Lot, не должно оставаться исключительно на клиенте.

Legacy-структуры для явного вывода из эксплуатации (после миграции, не сейчас): coffee-passport:lots и coffee-passport:roast-profiles в localStorage становятся read-only кэшем поверх Supabase, затем — источником для одноразового backfill, затем — не нужны. lib/data/lots.ts (seed-массив) перестаёт быть источником каталога, но может остаться как seed-скрипт для новой БД.

Сознательно не решается на Stage 3: DevRoleSwitcher и любой security-hardening; RLS-политики (в том числе для будущего мультиростерного разграничения записи — см. финальный вопрос); Events/Community/Gamification; редизайн Map; масштабирование Loyalty; recommendation engine; концепция Experiments; второй платящий ростер как операционный онбординг; любой новый UI; любые изменения в репозитории XO COFFEE; Visit/Session-объект, связывающий Tasting и Loyalty (раздел 20 задачи — архитектурная возможность названа в разделе E, не создаётся); полноценная миграция всех полей профиля Roaster/Coffee Shop (переносится только identity-якорь, необходимый для FK); количественный учёт остатков (раздел H).

N / Final Recommendation

Один вариант: пять таблиц, аддитивная миграция FK, тонкие Roaster/Coffee Shop

Ввести в Supabase пять новых таблиц — coffees, green_lots, lots, reference_roast_profiles (+ roast_batches отдельно от неё), reference_taste_profiles — вместе с двумя тонкими identity-таблицами roasters и coffee_shops, содержащими только то, что нужно для реальных внешних ключей (не полную миграцию существующих богатых профилей). lots.public_id сохраняет текущий читаемый формат, генерируется на сервере с реальным unique constraint. К checkins, recipes и cafe_menu_entries добавляются nullable FK-колонки рядом с существующими текстовыми — ничего не удаляется, ничего не переименовывается, ни один текущий UI-путь не меняется. Loyalty и Barista не получают новых связей с Lot. Мёртвая схема 0001 не используется и не трогается.

Это решение, которое можно утвердить или отклонить целиком — не пять равнозначных вариантов на выбор.

Final Question

Устойчива ли модель при 100 лотах, 10 кофейнях, тысячах дегустаций и нескольких ростерах через два года?

Да — с одной явно названной, а не спрятанной оговоркой.

FK-граф (Coffee→Green Lot→Lot→{Reference Roast Profile, Roast Batch, Reference Taste Profile}, Lot↔Coffee Shop, Lot→Recipe, Lot→Tasting) растёт добавлением строк, не изменением схемы — новый ростер, новая кофейня, новый лот не требуют новой таблицы или новой связи. Формат public_id уже кодирует ростера в самой строке, поэтому коллизии между ростерами исключены по конструкции, как только генерация становится серверной (раздел F). Coffee (происхождение) сознательно скоуплен на одного ростера — если два ростера закупают зерно с одной и той же фермы, это создаёт два отдельных Coffee-объекта, что коммерчески корректно (это разные продукты у разных продавцов), а не архитектурный дефект.

Где модель ломается без дополнительной работы — честно, не скрыто: ничего в этом документе не проектирует, кто именно может писать в чужой Lot/Green Lot/Roast Profile при нескольких ростерах на одной платформе одновременно — это вопрос RLS-политик (правило 21, явно вне периметра Stage 3), а не схемы данных. Схема готова к множеству ростеров; изоляция записи между ними — отдельная, обязательная, но чисто аддитивная задача поверх уже готовой схемы, не её переделка.
