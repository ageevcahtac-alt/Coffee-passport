# Аудит пути зерна — 2026-11-03

**Задача:** аналитический аудит (код НЕ менялся, миграций нет). Экосистема:
Coffee Passport (этот репозиторий) + XO COFFEE Admin (источник истины
заказов/производства) + XO Store (витрина, read-only потребитель лотов).

**Заявленная бизнес-логика владельца:** (1) ростерия создаёт и активирует
канонический лот; (2) кофейня и магазин видят активированный лот; (3) для
заказа кофейни магазин добавляет лот на витрину и активирует у себя;
(4) логистикой и учётом движения зерна занимается админка магазина, НЕ
ростерия. Замысел — безопасность: исключить манипуляции ростерии/кофеен
с зерном и заказами.

## 1. Фактический путь зерна (по коду)

### Лот (живёт в БД паспорта)

```
[coffee] 1─N [green_lots] 1─N [lots: status draft→testing→active→archived,
                               in_roaster_catalog]
```

1. **Создание.** Ростерия в кабинете (`app/dashboard/roaster/new/page.tsx`,
   `components/roaster/GreenLotForm.tsx`) создаёт Coffee → Green Lot
   (`purchased_kg` — свободное число, без дальнейшего учёта расхода) → Lot
   (`status='draft'`, `lib/data/canonicalLotStore.ts:347-378`). RLS-запись
   только roaster_admin своей ростерии
   (`0025_canonical_lot_rls.sql:27-41, 108-112`, функция
   `is_roaster_staff_for`).
2. **Активация.** `CanonicalLotStatusControl.tsx:61-83` — клиентский
   переключатель статуса; единственный серверный «гейт» —
   `isReadyForActive` (name + qGrade > 0), и тот в браузере
   (`CanonicalLotStatusControl.tsx:35-37`). Прямым PATCH через PostgREST
   ростерия может поставить любой статус — RLS это не ограничивает.
3. **Публикация магазину.** XO Store сам тянет GET
   `/api/integrations/xo-store/lots` (Bearer `XO_STORE_INTEGRATION_SECRET`,
   fail-closed без секрета — `lib/integrations/xoStoreAuth.ts:8-13`),
   ростерия жёстко зашита (`XO_ROASTER_SLUG='roaster-xo'`), фильтр
   `status='active' AND in_roaster_catalog=true`
   (`app/api/integrations/xo-store/lots/route.ts:75-81`). Push-направления
   из паспорта в Store **нет**.
4. **Появление у кофейни.** (а) Меню кофейни: запись `cafe_menu_entries`
   разрешена только на active+in_catalog лоты (гейт RLS
   `0030_cafe_menu_ordering_gate_rls.sql`); (б) каталог для заказа —
   через Admin (`xoAdmin.catalog()`), позиции связаны с каноническим лотом
   через `passport_public_id` (`lib/integrations/xoAdmin.ts:115`).

### Заказ и движение зерна (живут в XO Admin; паспорт — тонкий прокси,
### локальной копии заказов/остатков в БД паспорта НЕТ — проверено grep по
### миграциям: таблиц order/production/ship/stock/ledger нет)

5. **Заказ кофейни.** `app/dashboard/cafe/(hub)/orders/new/page.tsx`
   → POST `/api/cafe/roastery-orders/route.ts:33-55`: роль
   `requireStaffApi('cafe_admin')`, кофейня берётся из профиля сессии,
   тело содержит только `variant_id`+`quantity` (≤50 строк, ≤1000/строка,
   цены/вес/название серверно не принимаются —
   `lib/orders/roasteryOrders.ts:338-389`) → `xoAdmin.createShopOrder`
   с `idempotency_key`.
6. **Производство ростерией.** Очередь GET `/api/roaster/production`,
   переходы POST `/api/roaster/production/[id]/transition/route.ts:15-35`:
   роль roaster_admin, цепочка `queued → in_production → produced(units) →
   ready_for_shipping → shipped(units)` (`lib/orders/roasteryOrders.ts:173-187`);
   количество вводится только на produced/shipped, валидация границ —
   клиентская, финальная — в Admin («Admin re-checks scope, acceptance,
   status and quantity» — комментарий в route).
7. **Видимость.** Кофейня видит свои заказы и стадию
   (`shopOrderStage`, `lib/orders/roasteryOrders.ts:190-208`): cancelled /
   completed / new («Ожидает подтверждения XO COFFEE») / производство /
   отгружен. Подтверждения **приёмки** кофейней в модели нет.

### Соответствие заявленной логике 1–4

| # | Заявлено | Факт | Вердикт |
|---|---|---|---|
| 1 | Ростерия создаёт и активирует лот | canonicalLotStore + RLS своей ростерии | ✅ |
| 2 | Кофейня и магазин видят активированный лот | кофейня — меню (гейт 0030) + каталог заказов; магазин — pull read-only | ✅ |
| 3 | Для заказа кофейни магазин добавляет лот на витрину и активирует у себя | **В паспорте стороны магазина в заказе нет**: заказ кофейни идёт напрямую в Admin (`createShopOrder`), не через витрину/активацию магазина. Магазин — read-only потребитель списка лотов | ⚠️ расхождение: пункт 3 в этом репозитории не реализован и не проверяем; возможно, живёт в XO Store/Admin |
| 4 | Логистика и учёт — админка магазина, НЕ ростерия | заказы/статусы/количества/audit — в Admin; ростерия двигает только свои production-статусы (своя зона ответственности) | ✅ (с оговоркой: «админка магазина» в коде — это Admin, не Store) |

Расхождение по п.3 зафиксировано как находка F-1: заявленной контрольной
точки «магазин активировал лот» в коде паспорта нет — заказ возможен вне
зависимости от витрины магазина. **Решение владельца 2026-11-03: F-1 — не
дыра, а граница систем** — активация лота на витрине реализована в XO
Store/Admin (вне этого репозитория); паспорт остаётся read-only источником
списка лотов. Действий по паспорту не требуется.

## 2. Безопасность (может ли ростерия/кофейня обойти админку)

**Что проверено:** RLS-политики лотов/меню (0025, 0017, 0030), гейты ролей
(`requireStaffApi`), поверхность API обеих интеграций, service-role
использование.

- **Заказы через Supabase-обход невозможны в принципе:** таблиц заказов,
  производства и остатков в БД паспорта нет — нечего править через
  anon/authenticated ключ. Вся мутация заказов проходит через Admin, который
  сам перепроверяет scope (roaster_id/coffee_shop_id), acceptance, статус и
  количество (`lib/integrations/xoAdmin.ts:3-8`, комментарии в роутах).
- **Scoped id только из сессии** — гейт 3 (CLAUDE.md) соблюдён:
  `requireStaffApi` берёт `cafe_id`/`roaster_id` из `profiles`
  (`lib/auth/requireStaffApi.ts:39-65`); тело запроса не может назвать
  другую кофейню (валидация `parseCafeOrderRequest` не принимает id магазина
  вообще — `lib/orders/roasteryOrders.ts:338-344`).
- **Кофейня не может прикрепить к меню неактивный лот:** RLS-гейт 0030
  (insert только `status='active' AND in_roaster_catalog=true`). Обход
  клиентского UI прямым INSERT закрыт политикой.
- **Ростерия может писать только свои строки** (is_roaster_staff_for),
  DELETE-политик нет нигде — удаление закрыто по умолчанию.
- **Service role** (`lib/supabase/adminClient.ts`) в пути зерна не
  используется — только admin/cron/barista-API вне этой цепочки.
- **Пилотный kill-switch выключен не полностью:** `0029` оставляет
  `pilot_demo_enabled=true` — RPC `dev_seed_staff_profile` (самоназначение
  ролей через PostgREST, 0008) открыт до ручного
  `update app_settings set value=false`. До онбординга реальных аккаунтов —
  ок, после — действие владельца.

**Вывод:** манипуляции с заказами/количествами/статусами движения со стороны
ростерии и кофеен через паспорт невозможны. Риски качества данных, не
безопасности: ростерия может активировать неготовый лот прямым PATCH
(обход клиентского `isReadyForActive`) — RLS не проверяет qGrade.

## 3. Отказ магазина / внешних систем

- **XO Store недоступен:** паспорт не замечает — интеграция pull-only со
  стороны Store. Входящий endpoint живёт в паспорте; упавший магазин просто
  не забирает лоты. Потери нет; после восстановления магазин подтянет
  актуальный снапшот (`force-dynamic`, без кэша — `route.ts:19`).
  Fail-closed на входе: нет/неверный секрет → 401 (`xoStoreAuth.ts:9-12`,
  тесты `route.test.ts:177-196`), гейт 5 соблюдён.
- **XO Admin недоступен (для кофейни):** каталог, список заказов и создание
  заказа отвечают единым `admin_unavailable` 503 без причины
  (`lib/integrations/xoAdmin.ts:54-57, 96-98`). **Заказ блокируется целиком,
  локально ничего не сохраняется** — это ровно fail-closed из гейта 5.
  Кофейня видит: «Система заказов XO COFFEE сейчас недоступна…» и подсказку,
  что повтор безопасен (`orders/new/page.tsx:128-132`).
- **Идемпотентность:** ключ генерится на черновик и перегенерируется при
  любом его изменении (`orders/new/page.tsx:66-73`); по контракту Admin
  отвечает уже созданным заказом на повтор того же ключа. Отвал после
  коммита в Admin (таймаут 10 с) → клиент показывает unavailable → повтор с
  тем же ключом не задваивает заказ. **Окно дубля:** повтор с НОВЫМ ключом
  после таймаута создаст второй заказ — UI это не блокирует (ключ не
  меняется, пока черновик не тронут, так что штатный retry безопасен).
- **Ретраев/очереди нет:** один вызов, нет ни повторных попыток, ни outbox.
  При долгом дауне Admin кофейня полностью теряет оперативность по заказам
  (создание + история), но не данные: источник истины цел, после
  восстановления всё консистентно.

## 4. Точки потерь зерна (где «исчезает» без записи)

1. **Нет сквозного журнала движения зерна.** `green_lots.purchased_kg`
   (`0022:79`) — статичное число: производство/отгрузка его никак не
   уменьшают, связи «сколько зерна ушло в конкретное производство» в
   паспорте нет. Количественный след живёт только в Admin.
2. **Нет подтверждения приёмки.** После `shipped` нет шага «кофейня
   приняла»: расхождение отгружено/доставлено никем не фиксируется,
   `completed` ставит Admin (`OrderStatus` в `lib/orders/roasteryOrders.ts:31`).
3. **Частичная отгрузка не является инцидентом.** `produced_units`/
   `shipped_units` вводит ростерия; UI подсвечивает лимиты
   (`components/orders/ProductionAction.tsx:35-38`), но формального правила
   «shipped ≠ ordered → инцидент» нет ни в паспорте, ни в видимой части
   контракта Admin.
4. **Отмены/возвраты без обратного движения.** События
   ORDER_CANCELLED/PRODUCTION_CANCELLED с причиной есть (`roasteryOrders.ts:148-159`),
   но возврат зерна «на склад» нигде не пишется — физический остаток
   существует только в учёте Admin, вне этого репозитория.
5. **Ручные правки в Admin не прозрачны для паспорта** — by design (копии
   нет), но и механизма сверки нет: пассивное расхождение не обнаружится.
6. **Магазин вне контура учёта:** его витринные продажи (если со склада
   магазина) в путь зерна здесь не попадают вовсе.
7. Качество данных: активация лота в обход `isReadyForActive` (п.2
   безопасности) — не потеря зерна, но «невалидный» лот попадает в заказы
   кофеен и витрину.

## Предложения (без кода)

Оценки: S < 0.5 дня, M 1–2 дня, L 2–4 дня.
**Статус 2026-11-03 (решения владельца):** P-1…P-4 (учётный контур:
приёмка, ledger, сверка, очередь) — **отложено**, до отдельного решения о
том, где живёт учётный контур (в паспорте или в Admin). P-5 — принято,
реализуется сразу (серверный гейт активации лота, ветка
`chore/grain-audit-followups`). P-6 — принято как действие владельца при
онбординге (раздел ниже).

**P-1. Двустороннее подтверждение отгрузки (приёмка кофейней).**
Новый шаг `delivered → accepted` в производстве: кофейня подтверждает
получение (с количеством), расхождение с `shipped_units` автоматически
порождает инцидент, видимый обеим сторонам и владельцу.
- Схема/код: паспорт — `POST /api/cafe/roastery-orders/:id/confirm-receipt`
  (requireStaffApi cafe_admin, qty) + метод `xoAdmin.confirmReceipt` +
  кнопка в `app/dashboard/cafe/(hub)/orders/page.tsx` + тесты; Admin —
  новый статус/событие ORDER_RECEIVED + правило инцидента.
- Объём: M (паспорт) + M (Admin).

**P-2. Сквозной журнал движения зерна (ledger).**
Иммутабельная таблица `grain_movements` (по образцу `roast_batches`:
insert-only + триггер-запрет UPDATE/DELETE, `0023:84-97`): `lot_id`/
`public_id`, вид (purchase/production/shipment/receipt/return/adjustment),
количество, автор (роль+id), причина, ссылка на заказ/производство.
Писать — из переходов production и приёмки; читать — своя ростерия и
владелец.
- Схема: новая миграция `0037` (таблица + триггер + RLS select public /
  insert через security-definer-RPC или из server routes с service role);
  код — запись в роуте transition и в confirm-receipt.
- Объём: L. Закрывает F-2/F-3 в части следа.

**P-3. Сверка остатков (reconciliation).**
View/отчёт «заказано vs произведено vs отгружено vs принято» per lot/order +
страница в `/admin` и флаг расхождения. Источник — ledger (P-2) +
production из Admin.
- Схема: view поверх ledger (+ опционально cron-снапшот состояний Admin).
- Объем: M. Закрывает пассивные расхождения (F-3).

**P-4. Поведение при недоступном Admin/Store — очередь.**
Outbox-таблица в паспорте: при `admin_unavailable` создание заказа
складывается в очередь (тот же idempotency_key), cron/worfklow (`events-cron`
уже есть) дожимает. Кофейня видит «в очереди», а не ошибку. Альтернатива
дешевле: авто-повтор на клиенте с тем же ключом 2–3 раза с бэкоффом.
- Схема: таблица `outbox_jobs` + дожим в существующем cron; или только
  клиент.
- Объём: M (таблица+cron) / S (клиентский retry). Закрывает F-4.

**P-5. Серверный гейт активации лота.**
Перенести `isReadyForActive` с клиента на сервер: RPC `activate_lot(public_id)`
(security definer, проверка name+qGrade) вместо прямого UPDATE статуса; RLS
UPDATE на `lots.status` оставить только через RPC ( revoke прямого update
статуса либо with-check на уровне полей невозможен — проще RPC+grant).
- Объём: S. Закрывает F-5.

**P-6. Выключить пилотный kill-switch при онбординге.**
`update app_settings set value=false where key='pilot_demo_enabled';` —
ручное действие владельца в Supabase при появлении первых реальных
аккаунтов. Закрывает F-6.

Приоритет владельцу (на момент аудита): P-2+P-1+P-3 (учёт и контроль
движения), затем P-4, P-5, P-6 — по готовности.

## Действие владельца при онбординге (P-6, accepted 2026-11-03)

При появлении первых реальных (не пилотных) аккаунтов staff выключить
пилотный kill-switch RPC `dev_seed_staff_profile` (0008) одной командой в
Supabase SQL Editor / dashboard — без деплоя кода (0029):

```sql
update public.app_settings
set value = false, updated_at = now()
where key = 'pilot_demo_enabled';
```

Проверка результата: `select key, value from public.app_settings where key = 'pilot_demo_enabled';` → `value = false`. После этого прямой вызов RPC через `/supabase/rest/v1/rpc/dev_seed_staff_profile` перестаёт создавать staff-профили.

Продублировано в пилотном чек-листе: `docs/audits/CODEX_PREPILOT_IMPLEMENTATION_REPORT.md` (раздел про `pilot_demo_enabled`).
