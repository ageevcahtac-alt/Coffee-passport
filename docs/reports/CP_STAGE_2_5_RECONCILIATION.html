00 / Executive Summary

Продукт крепче, чем документы о нём предполагали — кроме одной незаживающей раны

Сверка трёх документов и кода показывает: расхождение Stage 1 → 2.0 меньше, чем ожидалось (большинство доменов уже существовали и уже были задокументированы на момент Stage 1); Stage 2 остаётся архитектурно верным почти во всём, кроме одной предпосылки — что Lot к моменту интеграции станет реальной таблицей. Этого не произошло. Это и есть главный вопрос Stage 3.

Не новый продукт

Barista, Loyalty, Recipes, Map, Events уже существовали и уже были в фокусе Stage 1 — «рост» между документами меньше, чем предполагала исходная постановка задачи (раздел 02)

Второй core loop подтверждён

Loyalty — не просто фича: атомарные RPC, реальные деньги, ежедневный инструмент бариста. Stage 1 назвал это PREMATURE; факты это не подтверждают для уже работающего пилота (раздел 08)

Lot — незажившая рана

Stage 1 (P1) и Stage 2 (шаг 3) оба требовали перевести Lot в реальную таблицу. Ни один коммит между документами этого не сделал (раздел 06, 15)

Новый критический риск

Ни Stage 1, ни Stage 2 не рассматривали продакшн-безопасность. 2.0 Audit нашёл активный обход авторизации, не упомянутый ни в одном документе (раздел 13)

01 / Current State

Coffee Passport 2.0 как техническая и продуктовая система — без vision, без рекламы

Реальные роли

FACT Пять значений enum на одной таблице profiles: enthusiast, barista, cafe_admin, roaster_admin, admin. Ни одна роль — не отдельная бизнес-сущность с собственной таблицей identity.

Реальные сущности

FACT В Supabase реально живут: profiles, checkins, recipes (BrewingRecipe), equipment_garage, barista_profiles, shop_ranks/guest_shop_statuses/subscriptions/loyalty_transactions, cafe_menu_entries, checkin_replies, events, shop_mute_preferences.

Работающие сценарии

FACT Слепая дегустация → checkins; продажа/списание лояльности → атомарные RPC; живое меню кофейни с автоистечением; анонимизированная аналитика roaster/cafe.

Частично работающие

FACT Кастомные устройства (approve-функция без вызывающего UI); QR-страница участника (заглушка); партнёрская активация (создаёт запись, не аккаунт).

Demo / mock / static

FACT Весь каталог Lot/Roaster/CoffeeShop/Barista — localStorage поверх seed-массива; 4 захардкоженных demo-аккаунта + безусловный DevRoleSwitcher; LegacyLotCreator целится в несуществующую таблицу.

В Supabase vs localStorage

FACT Supabase: tasting/loyalty/menu/events/feedback — операционный слой. localStorage: каталог (Lot/Roaster/Shop/Barista identity), личные рецепты, cupping-журнал, голосование — идентичность и «второй мозг» гостя.

Связанные vs независимые данные: связаны реальным FK — profiles↔checkins, checkins↔checkin_replies, subscriptions↔loyalty_transactions. Связаны только совпадением текстовой строки, без FK — Lot↔recipes, Lot↔cafe_menu_entries, Lot↔checkins. Полностью независимы — KitchenRecipe, cupping-журнал, recipe voting, custom coffees.

04 / What Is The True Product Loop?

Два core loop, не один — и это не совпадение, а честная находка

A. Main Product Loop

Guest Blind Tasting Loop. Lot/контекст → BlindTastingLock → слепая оценка (адаптивная по типу напитка) → checkins → reveal/сравнение с эталоном → journey-история гостя → анонимная аналитика ростеру/кофейне. Это определяющий, идентичность-образующий цикл продукта — без него Coffee Passport перестаёт быть Coffee Passport.

B. Secondary Core Loop

Loyalty Loop. Guest QR → Barista scan → RPC sell/redeem → ранг/скидка/retention → повторный визит. Атомарен, денежен, ежедневно используется бариста. Не питает Tasting Loop данными и не питается им — работает параллельно, вокруг той же пары (гость, кофейня).

C. Supporting Loops

  • — Cafe Analytics/Benchmark: усиливает Tasting Loop решениями по ассортименту
  • — Roaster Feedback: усиливает Tasting Loop обратной связью по эталону
  • — BrewingRecipe (привязанный к Lot): усиливает контекст дегустации и авторство бариста

D. Peripheral Features

KitchenRecipe и cupping-журнал (личные, localStorage, несвязанные), Equipment «гараж», Map, Events, Community-голосование, партнёрский CRM. Все реальны, ни один не является условием, при отсутствии которого продукт перестаёт быть собой.

Почему это два loop, а не один с довеском: у них разные владельцы данных (гость сам себе vs. бариста над гостем), разная природа записи (сенсорная оценка vs. денежная транзакция) и разная частота (разовая дегустация лота vs. предположительно многократные визиты). Слияние их в один «цикл» было бы искусственным упрощением — архитектура кода уже честно держит их раздельно (нет FK между checkins и loyalty_transactions).

05 / Critical Question: What Is Coffee Passport?

«Слой данных» — да. «Инфраструктура консолидации рынка» — пока нет

«Цифровой слой данных Specialty Coffee»

DECISION: остаётся верным — это буквально то, что делает Tasting Loop: превращает субъективный опыт в структурированные, сравнимые данные (4 оси + дескрипторы + контекст).

«Инфраструктура консолидации рынка вокруг реального вкуса»

DECISION: требует уточнения — «рынок» подразумевает множество ростеров и кофеен. Сегодня это один ростер, одна кофейня, без self-serve онбординга второго. Формула описывает цель, не текущее состояние.

Почему уточнение нужно именно теперь, а не раньше: до появления Loyalty как второго реального core loop формула «слой данных» была достаточной — продукт был исключительно про сбор и сравнение вкуса. Barista + Loyalty добавили второй, денежный, retention-ориентированный примитив, которого «слой данных» не описывает вовсе. Игнорировать это — занижать то, чем продукт стал; называть это «консолидацией рынка» — завышать то, чем он ещё не стал (нет второго платящего партнёра, нет живой таблицы организаций).

Уточнённая формула: Coffee Passport — операционный слой «вкус + удержание» (tasting + loyalty) для пары ростер↔кофейня, доказанный на одном пилоте, спроектированный так, чтобы стать межкофейной/межростерной инфраструктурой specialty coffee, но ещё не являющийся ею технически (нет живых таблиц организаций, нет self-serve онбординга, нет второго партнёра).

06 / Lot — Final Architectural Status

Ни identifier, ни product object, ни центральная сущность — соглашение об именовании без веса схемы

Это самый важный вывод документа: три источника (Stage 1 P1, Stage 2 раздел 04+13, 2.0 Audit §06/§17) независимо приходят к одному и тому же факту, и ни один из них не смог сдвинуть его с места.

Архитектурная проблема, зафиксированная без предложения решения: Lot сегодня — это текстовое соглашение об именовании, последовательно уважаемое во всех местах, где он упоминается (recipes, cafe_menu_entries, checkins, QR), но нигде не защищённое ссылочной целостностью Postgres. Он ведёт себя как canonical identifier в UX (одна и та же строка узнаётся везде), но не является ни product object на уровне БД (нет таблицы со своими столбцами/ограничениями), ни центральной сущностью экосистемы в смысле FK-графа (граф FK вокруг него попросту пуст). Это не новая находка этого документа — это единственная находка, которую все три предыдущих документа сделали независимо и ни разу не закрыли.

07 / Barista — First-Class Role?

Роль, ведущая себя как сущность — но масштаб пока не требует делать её сущностью

ВопросОтвет

Должен ли Barista стать полноценной сущностью? HYPOTHESIS: не сейчас. Ровно та же логика, что Stage 1 применил к второму ростеру («сначала таблица нужна, когда появится второй реальный кейс») применима здесь: сегодня нет ни одного зафиксированного бизнес-сценария, где один бариста реально работает в двух кофейнях. Делать Barista отдельной сущностью заранее — не поддержанное конкретным сценарием усложнение. Вопрос стоит пересмотреть, если появится хотя бы один реальный кейс мультикофейного бариста или найм бариста как отдельного маркетплейса.

08 / Loyalty — Second Core System?

Да, для существующего пилота. Нет, для расширения на новые кофейни — сейчас

Что работает реально

Ранги (shop_ranks), статус гостя (guest_shop_statuses), абонементы (subscriptions), транзакции (loyalty_transactions) — все четыре таблицы реальны, RLS без единого клиентского права записи.

RPC / транзакционность

loyalty_sell_subscription и loyalty_redeem — SECURITY DEFINER, SELECT … FOR UPDATE внутри одной транзакции. Классическая гонка двойного списания закрыта корректно на уровне БД, не на уровне UI.

Карты / номиналы

FACT Реальные номиналы — 1000/1500/3000/5000 ₽ (не 1000/2000/3000/5000, как предполагала постановка задачи) — это UI-кнопки, RPC принимает любой nominal > 0.

Связи

Guest — через QR-идентичность; Coffee Shop — через cafe_id-скоуп на всех политиках; Barista — как исполнитель транзакции (barista_id в логе).

Loyalty — второй core loop или просто фича? DECISION: второй core loop для уже существующего пилота, PREMATURE для масштабирования. Почему: (1) это единственный домен продукта с атомарной, денежно-надёжной серверной логикой — по инженерной зрелости он превосходит сам Tasting Loop; (2) дашборд бариста реально построен вокруг него как ежедневного инструмента, а не витрины; (3) но у него нет ни одной живой кофейни, кроме пилотной — расширение (новые ранги, новые кофейни, публичные балансы) решает проблему масштаба, которого пока нет, что дословно повторяет предупреждение Stage 1 «раздел 18». Различие с классификацией Stage 1 — не в факте (Loyalty реален), а в статусе (Stage 1 недооценил, что уже работающий пилотный loop может быть CORE без того, чтобы быть готовым к расширению.

09 / QR Architecture 2.0

Два контура, разная природа доверия — объединять сейчас не нужно

Lot QR

FACT Публичный, без аутентификации, идентифицирует продукт (Lot), ведёт на /passport/[lotId]. Модель доверия: «кто угодно может знать, что это за кофе».

Guest / Loyalty QR

FACT Персональный, некриптографический UUID (coffeepassport-guest:uuid), но каждое действие над ним гейтится RPC-проверкой роли и cafe_id сканирующего. Модель доверия: «UUID — сам по себе credential, как физическая карта».

Нужно ли их объединять? DECISION: нет, оставить независимыми. Они идентифицируют категорически разные вещи — товар vs. человека — и объединение публичного, некриптографического Lot QR с персональной идентичностью гостя создало бы риск деанонимизации без какой-либо продуктовой выгоды.

GAP / POSSIBLE FUTURE ARCHITECTURE Сценарий «Lot QR → Guest → Tasting → Barista → Loyalty → Coffee Shop → Analytics» как ЕДИНЫЙ прослеживаемый флоу сегодня не существует. Гость сканирует Lot QR сам по себе (начинает дегустацию); бариста сканирует Guest QR отдельно (лояльность). Между checkins.id и loyalty_transactions.id нет ни FK, ни общего session-объекта — это два параллельных действия за один визит, не одна цепочка. Связать их в один прослеживаемый визит — валидная будущая архитектура, но требует нового понятия «визит/сессия», которого сейчас нет ни в схеме, ни в UI.

10 / Taste Architecture 2.0

4 оси остаются каноном — не потому что мы так решили сейчас, а потому что решение уже принято и подтверждено

DECISION (Stage 2, подтверждено 2.0 Audit) Кислотность/Сладость/Тело/Горечь остаются единственными sensory dimensions — числовыми осями, которые вслепую сравниваются гость↔эталон. 0021 (milk-drink) не добавила пятую базовую ось — она добавила адаптивный, категориально-зависимый слой (milkBalance/coffeeReadability/creaminess для молочных напитков, aftertaste для чёрного кофе), ровно по паттерну, который Stage 2 уже придумал для XO-«finish». Пятую ось добавлять не нужно — механизм расширения без изменения канона уже работает и уже был использован независимо от XO-интеграции.

Descriptors (не числовая ось)

10 фиксированных тегов + под-дескрипторы флейвор-колеса + 5 дефектов. Покрывает то, что XO называет «aroma», без принуждения нетренированного гостя оценивать это числом.

Context / Preparation

drinkCategory/drinkType/milk-tree фиксируются ДО дегустации как контекст, не как sensory dimension. BrewingRecipe (метод/дозировка/температура) — соседний, но архитектурно отдельный домен (раздел 10 ниже).

15 / Core vs Supporting vs Periphery — Final Classification

CORE

Guest Blind Tasting Loop; sensory-модель (4 оси + дескрипторы + адаптивный слой); ролевая RLS-модель; checkins как единица данных.

CORE 2

Loyalty Loop — второй фундаментальный, атомарный, денежный цикл, центральный для ежедневной работы бариста.

SUPPORTING

BrewingRecipe, Equipment, Cafe Analytics/Benchmark, Roaster Feedback, announcement TTL/mute, Barista как роль.

ECOSYSTEM

Map, партнёрский CRM/онбординг — раскрывают потенциал при множестве кофеен/ростеров, которых пока нет.

PREMATURE

Events, Community-голосование, расширение Loyalty на новые кофейни, KitchenRecipe как community-слой.

PERIPHERAL

News (фактически отсутствует), Gamification (только текстовое поле), Experiments (не существует).

17 / XO Coffee × Pure Roast × Coffee Passport

Разделение ответственности не изменилось — 2.0 только укрепил границы

DOCUMENT (Stage 2, §03) XO Coffee — коммерческая витрина (каталог, discovery, покупка, checkout). Pure Roast — философия/метод обжарки, не продукт с интерфейсом. Coffee Passport — слой данных/опыта/экосистемы (passport, tasting, guest profile, barista, кофейня, лояльность, аналитика).

FACT, подтверждено 2.0 Audit Ничего из нового функционала (Barista, Loyalty, Map, Events, milk-drink) не размывает эту границу — все они однозначно принадлежат Coffee Passport, ни один не касается каталога/цены/checkout. Разделение ответственности не изменилось и не требует пересмотра после появления 2.0.

Это по-прежнему два отдельных проекта, две кодовые базы — без общего рантайма, без общей БД, без общей авторизации. Единственная точка соприкосновения — совпадение значения одной строки (Lot ID), и именно эта точка не готова физически (раздел 06).

19 / Stage 3 Proposal

Stage 3 —

The Canonical Lot Decision

Единственный архитектурный вопрос, который три предыдущих документа поставили независимо и ни разу не закрыли: каким должен быть Lot как сущность базы данных, и кто физически владеет им как источником истины?

Goal

Принять архитектурное решение о целевой схеме Lot (и минимально необходимых Roaster/Coffee Shop как реальных таблиц вокруг него) — без написания кода и миграций.

Why now

  • Это единственная зависимость, блокирующая шаг 3 из 7 в уже согласованной последовательности Stage 2
  • Это единственная рекомендация Stage 1 (P1), которая ни разу не была выполнена за весь прошедший период
  • Это единственный GAP, который независимо всплыл во всех трёх документах и в самом коде (recipes/menu/checkins — все текстовые ссылки без FK)
  • Продолжать наращивать функциональность (milk drinks, TTL, events) поверх этого долга — значит увеличивать площадь, которую придётся мигрировать позже

What it decides

  • Целевая схема таблиц Lot / Roaster / Coffee Shop как реальных сущностей Supabase
  • Формат и стабильность Lot ID (сохранить текущий читаемый формат или изменить)
  • Стратегия FK для recipes / cafe_menu_entries / checkins — какие связи становятся настоящими внешними ключами
  • Кто становится источником истины физически (не только по формулировке документа) — Passport, как решил Stage 2, или иначе
  • Путь миграции существующих localStorage-каталогов без разрушения работающего UI

What it does NOT decide

  • Статус Barista как отдельной сущности (раздел 07 — не сейчас)
  • Расширение Loyalty на новые кофейни (раздел 08 — не сейчас)
  • Судьбу DevRoleSwitcher и RLS-дыры profiles — операционные фиксы, не архитектурные решения, могут и должны решаться независимо и раньше
  • Concept Experiments, зрелость Map/Events/Community
  • Реализацию моста XO ↔ Passport — это следует ЗА этим решением, не входит в него
  • Любой код, любую миграцию, любой UI

Deliverables

  • Схема-предложение уровня ERD (не SQL) для Lot/Roaster/Coffee Shop
  • Оценка риска миграции существующих FK-подобных текстовых связей (recipes.lotId, cafe_menu_entries.lot_id, checkins.lot_id)
  • Явное решение по владению источником истины
  • Явный список того, что Stage 3 сознательно не решает (раздел «What it does NOT decide» выше, зафиксированный как часть deliverable)

Acceptance criteria

  • Схема согласована архитектором(ами) продукта, без кода/миграций, написанных в рамках этапа
  • Явный go/no-go для последующего этапа реализации (Stage 4)
  • Ни один существующий работающий UI-путь не должен требовать изменений для того, чтобы это решение считалось принятым — миграция данных остаётся отдельной, последующей работой
20 / Final Executive Summary

Десять вопросов — десять коротких ответов

1.
Что такое Coffee Passport 2.0 сейчас?

Операционный слой «вкус + удержание» для одной пары ростер↔кофейня, доказанный кодом, ещё не ставший межкофейной инфраструктурой.

2.
Главный продуктовый цикл?

Guest Blind Tasting Loop — слепая дегустация → checkins → сравнение с эталоном → journey-история.

3.
Есть ли второй core loop?

Да — Loyalty Loop, атомарный и денежный, центральный для ежедневной работы бариста.

4.
Что такое Lot?

Текстовое соглашение об именовании, уважаемое везде в UX, не защищённое ни одной ссылочной связью в базе данных.

5.
Кто такой Barista в архитектуре?

Роль на общем профиле с реальным операционным весом (loyalty-терминал, авторские рецепты) — пока не отдельная сущность, и масштаб этого не требует.

6.
Насколько важна Loyalty?

CORE 2 для существующего пилота; PREMATURE для любого расширения за его пределы.

7.
Как устроена Taste Architecture?

4 канонические числовые оси + дескрипторы + адаптивный категориальный слой поверх них (milk-drink, aftertaste) — механизм расширения без изменения канона уже работает.

8.
Какие функции периферийны?

News (фактически отсутствует), Gamification (текстовое поле), Experiments (не существует), Events и Community (реальны, но PREMATURE).

9.
Что сломано/не согласовано архитектурно?

Lot без ссылочной целостности (структурно); DevRoleSwitcher в продакшне (операционно-критично, отдельно от Lot).

10.
Какой вопрос должен решать Stage 3?

Каноническая схема и владение Lot как реальной сущностью базы данных — единственная зависимость, блокирующая всё остальное.
