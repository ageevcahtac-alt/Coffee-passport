Coffee Passport 2.0 — аудит текущего продукта

Полная фиксация фактического состояния кода и базы данных на сегодняшний день. Не заменяет Stage 1 и не меняет Stage 2 — это новая независимая точка отсчёта для следующего архитектурного этапа.

Дата аудита: 2026-09-07 Ветка: main Миграций: 21 (0001–0021) Роутов: ~50 Компонентов: 119 Метод: прямое чтение кода/SQL, 8 параллельных доменных проходов
00

Принципы аудита

Единственный источник истины — фактический код и миграции Supabase. README, PRODUCT_BACKLOG.md и предыдущий Stage 1 документ используются только как вспомогательный контекст и никогда не принимаются за текущее состояние без проверки в коде.

FACT подтверждено кодом/БД напрямую
CODE реализовано, но не всегда «правильно» с точки зрения архитектуры
DECISION явное архитектурное решение, видно из комментариев/схемы
HYPOTHESIS вывод по косвенным признакам
MISSING ожидалось, но не найдено в коде
LEGACY существует, но не должно определять архитектуру
PREMATURE реализовано, ценность зависит от масштаба сети

Если UI существует без backend — это указано явно. Если таблица существует, но не используется — помечена LEGACY. Если связь между сущностями предполагалась, но не реализована — помечена MISSING. Расхождения между кодом и документами разрешаются всегда в пользу кода.

01

Текущее техническое состояние

Next.js 14 (App Router) + Supabase (Postgres/Auth/RLS), без выделенного бэкенд-сервиса. Значительная часть доменных данных всё ещё живёт в localStorage, с частичным «write-through» синхронизмом в Supabase там, где домен уже был переписан на реальные таблицы.

  • FACT middleware.ts закрывает /admin HTTP Basic Auth-ом на edge-уровне — это не проверяется Postgres RLS и не связано с ролями profiles.
  • FACT lib/supabase/adminClient.ts называется «admin», но использует anon-ключ — сервис-роль не сконфигурирована нигде в проекте.
  • CODE Значительная доля доменных данных (лоты, ростеры, кофейни-каталог, бариста-ростер, рецепты «Кухни», голоса за рецепты, дневник каппингов) — это localStorage-массивы, у части из них есть параллельный «write-through» в Supabase (меню кафе, чек-ины/tastings, лояльность, рецепты BrewingRecipe), у части — нет вообще.

Production-like vs demo vs legacy

Production-like

Loyalty-модуль (RPC + RLS), checkins/tastings, cafe_menu_entries с cron-истечением, events-модуль с cron-агрегацией, RLS-разграничение ролей.

Demo / pilot

Весь каталог лотов/ростеров/кофеен/бариста — localStorage поверх seed-массивов; «Легаси»-конструктор лота на /admin; демо-инвайт-пароли партнёров; фиксированный DevRoleSwitcher.

Legacy

Вся схема миграции 0001 (users/roasters/coffees/lots/reviews) — по признанию самой миграции 0004, никогда не была применена к реальной БД.

Риск безопасности, обнаруженный при аудите: компонент components/dev/DevRoleSwitcher.tsx рендерится безусловно в корневом layout.tsx на каждой странице продакшн-сборки (по собственному комментарию в коде — «это и есть демо-режим приложения»). Любой посетитель сайта без единого пароля может одним кликом войти как barista, cafe_admin, roaster_admin или admin. Подробнее — §18 и §24.

Полная архитектура ролей

FACT Все пять ролей — это не отдельные бизнес-сущности, а значения одного enum-столбца role на единой таблице public.profiles (0007_staff_profiles_rls.sql), с текстовыми полями-скоупами cafe_id / roaster_id / barista_id, взаимоисключение которых проверяется constraint-ом profiles_role_scope_check.

РольТипСкоупСоздание аккаунтаRLS-периметр

FACT Помимо пяти ожидаемых ролей, в коде существует шестой, неформальный «слой ролей»: StaffMember.role (barista | confectioner | cook | administrator | manager, lib/data/staff.ts) — это чисто HR-карточка для UI команды кофейни, полностью на localStorage, никак не связана с auth/RLS.

Ни одна роль не является самостоятельной бизнес-сущностью в базе данных: нет таблиц roasters/coffee_shops/baristas с настоящими внешними ключами — только текстовые id-скоупы на общей таблице профилей, сопоставляемые построчно с localStorage-каталогами ростеров/кофеен/бариста.
04

Barista — роль/сущность 1.0

Самый развитый новый функционал продукта после Loyalty, но всё ещё роль на общем профиле, а не отдельная сущность.

Идентичность и профиль

  • FACT Статичный захардкоженный ростер из 9 бариста (lib/data/baristas.ts) + одна таблица barista_profiles (0015) — это тонкий слой личных предпочтений (любимое происхождение/метод/аватар), а не identity-таблица.
  • MISSING Self-service-приглашение нового бариста. generateInvitePassword.ts — прямо по комментарию в коде — не создаёт логин-доступный аккаунт. Реальное появление бариста — ручной SQL UPDATE profiles SET role='barista', cafe_id=…, barista_id=….
  • FACT Один бариста = ровно одна кофейня, работать в нескольких нельзя (нет join-таблицы, только скалярное поле).

Дашборд бариста

FACT Не демо: лояльность (RPC), фидбек от гостей (public.checkins, фильтр по baristaId), авторские рецепты (public.recipes, author_type='barista') — всё реально читается/пишется в Supabase. Статична только идентичность (имя/кофейня из seed-массива). Нет ни одного агрегированного stats-виджета (например, «средний рейтинг» / «чашек приготовлено») — только сырой список последних 5 отзывов.

QR-взаимодействие с гостем

FACT Полностью реализовано, но только для лояльности. Путь: BaristaLoyaltyPanel → камера (QrScanner) → extractGuestId() снимает префикс coffeepassport-guest: → fetchGuestProfile/fetchGuestShopContext → продажа абонемента или списание баллов через RPC loyalty_sell_subscription/loyalty_redeem.

MISSING «Сканирование гостя для привязки к дегустации» — этого не существует: TastingRecord.baristaId устанавливает сам гость, выбирая бариста из списка на последнем шаге своего собственного tasting-визарда, а не бариста сканированием.

Связи

СвязьСтатусКомментарий

EquipmentFACTтолько чтение общего «гаража» своей кофейни, личного инвентаря нет

08

Tasting & Sensory Architecture 2.0

Одна общая слепая sensory-модель с адаптивными, взаимоисключающими ветками по категории напитка — плюс отдельный, несвязанный «дневник каппингов».

Базовые оси (все категории напитка)

  • rating — 1–5 звёзд
  • guestFlavorProfile: acidity, sweetness, body, bitterness — слайдеры 1–5
  • bodyTexture — категориально: watery / medium / syrupy
  • sensoryTags — 10 фиксированных чипов + раскрываемые под-дескрипторы (флейвор-колесо)
  • defects — 5 фиксированных тегов (astringent/grassy/burnt/woody/over_bitter)
  • liked / disliked / note — свободный текст

Milk Drink Evaluation — что это архитектурно

FACT Это аддитивное расширение той же самой формы TastingForm, а не отдельная модель и не отдельный домен. По собственному комментарию миграции 0021_drink_evaluation.sql: «guestFlavorProfile намеренно не тронут… новые колонки чисто аддитивны».

УсловиеДополнительные оси (1–5, nullable)
drinkCategory === 'milk_based'milkBalance («баланс кофе и молока»), coffeeReadability («читаемость кофе через молоко»), creaminess («сливочность»)

Идентичность напитка (не сенсорика, фиксируется до дегустации): drinkCategory, drinkType, customDrinkName, milkBaseType (cow/plant), cowMilkType, isLactoseFree, fatContentPercent, plantMilkType.

Параллельная сущность: cupping-журнал

LEGACY / отдельный домен Собственная форма (CuppingForm) с осями acidity/body/brightness (не bitterness/sweetness!) и SCA-подобным finalScore 60–100 — целиком localStorage, не привязан ни к Lot, ни к QR, ни к кофейне.

Recipes

В коде существуют две независимые системы рецептов, объединённые только общими именами полей в UI.

KitchenRecipe («Мои рецепты»)

только localStorage — создаёт только гость, без привязки к Lot/кофейне/ростеру. Поля: метод, гриндер, доза, вода, температура, помол, время, преинфузия, заметки, isTop (личный пин), isPublic (шаринг с сообществом). Без TDS/экстракции, без рейтинга.

BrewingRecipe (public.recipes)

Supabase, привязан к Lot — авторы: roaster / coffee_shop / barista / enthusiast. Есть measuredTdsPercent → расчёт Extraction Yield %, копирование через parentRecipeId («адаптировать под себя»), лимиты квоты (5 черновиков/метод, публикация не чаще раз в 14 дней — антиспам, не тарифные планы).

MISSING Единого «сравнения рецептов» между собой нет — есть только сравнение «моя чашка vs. чашка автора рецепта» по экстракции на одном графике.

LEGACY Голосование за рецепты (лайк/дизлайк, toggle-механика) — полностью на localStorage, нет персистентности в Supabase, хотя питает витрину «Топ-3 сообщества» и /top-recipes.

Experiments

MISSING как отдельная концепция. Поиск по всему репозиторию слова «эксперимент»/«experiment» находит только маркетинговый подзаголовок раздела Coffee Kitchen («полностью автономное пространство для домашних экспериментов») и одинаковый по духу комментарий в сторе — нигде нет ни таблицы, ни страницы, ни стора, ни UI-механики с этим названием.

Ни то, ни другое не смоделировано, не названо и не отделено от понятия «рецепт» ни в схеме, ни в UI. Роль Experiments в архитектуре продукта на сегодня — нулевая; вся итерация рецепта происходит через заметки и форк.

Equipment

FACT «Гараж» (EquipmentSetup) — это одна запись на владельца (не поштучный инвентарь): espresso-гриндер/машина/вода + filter-гриндер/вода + список любимых фильтр-девайсов. FACT Кастомные устройства: гость может добавить фильтр-брюер вне пресетов; появляется как approved: false до модерации; функция approveCustomDevice() существует в сторе, но UI, вызывающего её, в прочитанных файлах не обнаружено — возможно недособранный модерационный флоу.

Вопрос из ТЗОтвет
Может ли Barista получить данные, предназначенные только Cafe Admin?Частично — читать может (RLS часто объединяет barista/cafe_admin в один OR), писать конфигурацию (ранги, чужие профили бариста) — нет.
Может ли Guest увидеть данные другого Guest?Нет по всем owner-scoped политикам (auth.uid()=owner).

Крупнейший риск аудита — активный в продакшне обход авторизации: components/dev/DevRoleSwitcher.tsx рендерится безусловно в app/layout.tsx на каждой странице сайта, не спрятан за NODE_ENV. FACT lib/supabase/adminClient.ts вводит в заблуждение названием — использует anon-ключ, сервис-роль не сконфигурирована нигде.

Current Product Loops

Оригинальный Stage 1-loop (Lot → Roaster → Cafe → Guest → Tasting → Analytics) остаётся частью картины, но больше не является единственным или даже самым зрелым циклом в коде.

Loyalty Loop наиболее зрелый

Guest QR → Barista scan → RPC sell/redeem → ранг/скидка → возврат гостя. Замкнут и атомарен на уровне БД.

Guest Tasting Loop зрелый

Scan/выбор лота → blind tasting → checkins → passport reveal → journey-история. Реален (Supabase), но taste-passport агрегат считается вне сервера.

Cafe Operations Loop зрелый

Меню (реально) → чек-ины гостей → аналитика/бенчмарк → корректировка меню. Замкнут внутри кофейни.

Roaster Feedback Loop зрелый, но изолирован

Reference profile → анонимизированная аналитика ← Guest/Cafe. Нет пути назад в каталожный лот (тот же лот правится только вручную).

Barista Loop частично

Рецепты + фидбек + лояльность — но не замкнут на собственную атрибуцию дегустации (её ставит гость).

Recipe/Kitchen Loop незамкнут

Рецепт → голос сообщества (localStorage) — не проверяется дегустацией/оценкой, живёт отдельно от Tasting Loop.

Вывод: главный «продуктовый» цикл сегодня — не единый лот-центричный loop, а связка Guest Tasting Loop + Loyalty Loop внутри одной кофейни; Roaster вовлечён как поставщик каталога и получатель анонимной аналитики, но не как активный участник цикла лояльности/меню.

What Coffee Passport 2.0 Actually Is

Coffee Passport 2.0 — это слепой sensory-журнал гостя, привязанный к конкретной паре «лот × кофейня», усиленный работающим внутрикофейным механизмом лояльности, вокруг которого нарастает — но пока не срослась в единую систему — периферия из рецептов, оборудования, карты и событий.

Пять функций, которые определяют продукт сегодня

  1. Слепая, адаптивная по типу напитка sensory-оценка (§08), записываемая в реальную БД.
  2. Ролевая модель на единой таблице профилей с RLS, разделяющая видимость coffee-фидбека и service-фидбека (§03, §18).
  3. Атомарный, RPC-based модуль лояльности с рангами и абонементами внутри конкретной кофейни (§12).
  4. Анонимизированная, приватность-осознанная аналитика для ростера и кофейни, построенная на Postgres views (§06, §07).
  5. Journey/passport-хаб гостя, собирающий историю посещений и вкусовой профиль во времени (§05).

Чем это принципиально не является

Не coffee rating app

Оценка вслепую привязана к конкретному физическому визиту и кофейне, а не к абстрактному каталогу кофе как в Untappd-подобных сервисах.

Не loyalty app

Лояльность — надстройка над tasting-циклом, а не отдельный продукт; нет отдельного онбординга «просто ради баллов».

Не cafe CRM

Нет расписаний, payroll, складского учёта (сознательно, см. CLAUDE.md) — только гостевая аналитика и HR-карточка команды.

Не recipe database

Recipes — вторичны и разделены на 2 несвязанные системы, не являются точкой входа в продукт.

Не digital passport-документ

Нет генерации PDF/экспортируемого артефакта — «паспорт» это состояние страницы, не документ.

Не соцсеть

Нет комментариев, форумов, профилей-на-показ — единственная social-механика — голосование за рецепты.

Deliverable — итоговые блоки

Executive Summary

  1. Coffee Passport 2.0 — это слепой sensory-журнал гостя плюс работающий модуль лояльности внутри конкретной кофейни; всё остальное — периферия разной степени готовности.
  2. Роль Barista полностью реализована как первоклассная роль на общем profiles, но не имеет self-service онбординга и не является отдельной бизнес-сущностью.
  3. Canonical Lot как единая БД-сущность не существует — лот живёт в localStorage ростера с текстовым ID, соединяется с реальными Supabase-таблицами кофейни/дегустаций только по совпадению строки.
  4. Схема БД пережила незапланированную миграцию архитектуры: миграция 0001 (реляционная модель) никогда не применялась к живой БД; реальная схема — вторая, текстово-идентификаторная, начиная с 0004.
  5. Loyalty — самый архитектурно зрелый модуль продукта: атомарные SECURITY DEFINER RPC, отсутствие клиентских прав записи на денежные таблицы, корректная защита от гонки двойного списания.
  6. Milk Drink Evaluation — это аддитивное расширение единой sensory-модели, а не отдельный домен; при этом существует отдельный, несвязанный «дневник каппингов» со своей, отличающейся моделью осей.
  7. Recipes расщепились на две несвязанные системы: личную (localStorage) и мульти-авторскую, привязанную к лоту (Supabase).
  8. Experiments как продуктовая концепция не реализована вообще — есть только заметки и форк рецепта.
  9. Обнаружен активный в продакшне обход авторизации через DevRoleSwitcher — наивысший приоритет к рассмотрению независимо от прочих архитектурных решений.
  10. RLS-политика на profiles допускает персоналу любой кофейни читать имя и email любого гостя платформы, не только своих посетителей.
  11. Map устроена «кофейня-first»: нет сценария «где попробовать этот лот» — обратной связи от лота к точкам продаж.
  12. News/Community и Gamification ожидались как системы, по факту — не более чем алгоритмическая витрина и одно текстовое поле соответственно.
  13. Feedback-архитектура сознательно приватность-осознанная: ростер никогда не видит service-фидбек и личность гостя, только анонимизированные coffee-показатели.
  14. Partner onboarding — это B2B-лидоворонка с ручной активацией, не автоматизированный self-service; активация не создаёт настоящий аутентифицируемый аккаунт.
  15. Stage 2 Integration Architecture в основном подтверждается кодом (роли, tasting, loyalty), но требует пересмотра в части «Canonical Lot» как интеграционной точки — такой точки в базе данных на сегодня не существует.

Top Architectural Changes vs. Stage 1

  1. Появилась полноценная роль Barista с нуля (профиль, дашборд, лояльность, рецепты, фидбек).
  2. Появился весь модуль Loyalty с нуля — самый зрелый новый домен.
  3. Появился домен Coffee Kitchen (Recipes + Equipment), расщеплённый на 2 несвязанные системы.
  4. Появилась карта кофеен (не лотов) и модуль событий.
  5. Sensory-модель расширена адаптивной milk-drink веткой (аддитивно, не отдельным доменом).
  6. Понятие «Passport» расщепилось на 3 разных артефакта под одним словом.
  7. Произошла незапланированная смена архитектуры БД: реляционная схема 0001 заброшена в пользу текстово-идентификаторной модели.
  8. Canonical Lot как БД-сущность утрачен — заменён на localStorage-каталог + совпадение строковых ID.
  9. Появилась полная ролевая RLS-модель с осознанным разделением видимости coffee vs. service фидбека.
  10. Появился второй, независимый от Lot QR-контур — Guest/Loyalty QR.
  11. Появился платформенный admin-слой, но в двух несвязанных вариантах авторизации.
  12. Появилась приватность-осознанная анонимизированная аналитика (views) для ростера и кофейни.
  13. Появились антиспам-механизмы (квоты на рецепты, лимиты кастомных методов) — признак реальной эксплуатации, не только прототипа.
  14. Recipe voting и taste-profile-агрегация остались клиент-side, несмотря на наличие серверной инфраструктуры под них.
  15. Обнаружен продакшн-обход авторизации через демо-виджет переключения ролей — архитектурно значимая находка, не предполагавшаяся Stage 1.

What Remains Valid (из Stage 1 и Stage 2)

  • Базовый цикл Roaster → Lot → Cafe → Guest → Tasting → Analytics — концептуально подтверждён, хотя техническая реализация связей слабее, чем предполагалось.
  • Идея приватность-осознанного разделения coffee-фидбека (виден ростеру) и service-фидбека (виден только кофейне) — реализована и работает корректно.
  • Guest, Cafe, Barista, Tasting как понятия Stage 2 — все реализованы и по большей части превосходят ожидания Stage 1/2.
  • Loyalty как направление — полностью подтверждена и оказалась более зрелой, чем можно было предполагать на момент Stage 2.

What Needs Reassessment

  • Статус Canonical Lot — нужно совместное решение: вводить ли реальную БД-таблицу лота, или сознательно оставить его localStorage-каталогом ростера с явным протоколом синхронизации.
  • Судьба дублирующейся/мёртвой схемы БД (миграция 0001, осиротевшие reviews/user_taste_profiles из 0004) — оставить как исторический артефакт или спланировать удаление.
  • Объединение или официальное разделение двух recipe-систем и двух tasting/cupping-моделей.
  • Судьба DevRoleSwitcher — критически требует решения до какого-либо публичного/коммерческого использования продакшн-окружения.
  • Судьба RLS-политики широкого чтения profiles — сузить до shop-scope или оставить осознанно (с явным обоснованием доверия к QR-как-credential).
  • Нужна ли лот-центричная карта («где попробовать этот лот») как часть основного гостевого цикла, или это сознательно вне охвата.

Do Not Build Yet

  • Experiments как отдельная сущность — концепции нет, вводить её до решения по Recipes/Kitchen архитектуре преждевременно.
  • Gamification/achievements-движок — пока это текстовое поле, а не система; строить движок без ясного продуктового решения о его роли не нужно.
  • News/Community как полноценный домен — нынешняя алгоритмическая витрина не создаёт достаточного основания для форума/ленты.
  • Автоматизированный self-service онбординг партнёров/бариста — до тех пор, пока не решён вопрос реальной multi-tenant аутентификации.
  • Любая интеграция с XO / Pure Roast, завязанная на Canonical Lot ID, — до совместного решения по статусу Lot как БД-сущности (§23).
Критическое условие соблюдено: этот документ фиксирует фактическое состояние Coffee Passport 2.0. Он не переходит к Stage 3, не содержит кода, миграций или изменений существующих компонентов. Следующий шаг определяется отдельно, после совместного изучения этого артефакта.
