# Лояльность XO COFFEE — Этап 1: ядро контура «Зал»

Дата: 2026-11-11 · Ветка: `fix/pre-pilot-shortlist` · Миграция: `supabase/migrations/0039_loyalty_stage1_hall.sql`

Пересборка модуля лояльности (бывший 0012 «ранги + абонементы») по брифу владельца. База лояльности
пустая (0 гостей) — миграции гостевых данных не делались, старая лестница Bronze/Silver/Gold/Platinum
удалена полностью.

## Что реализовано

**1. Ранги v2 (7 рангов, контур «Зал», магазин `shop-xo-vsevolozhsk`)**

| Ранг | Порог трат за 30 дней | Кэшбэк | Цвет (шкала обжарки) |
|---|---|---|---|
| Первый глоток | 0 ₽ | 2% | `#7FA650` (зелёное зерно) |
| Любитель | 1 000 ₽ | 3% | `#D2B48C` |
| Дегустатор | 2 000 ₽ | 4% | `#B08968` |
| Ценитель | 3 000 ₽ | 5% | `#8B6B4A` |
| Знаток | 5 000 ₽ | 6% | `#6F4E37` |
| Энтузиаст | 8 000 ₽ | 8% | `#4E3429` |
| Хранитель вкуса | 10 000 ₽ | 10% | `#2D1E18` (глубокая тёмная) |

- Критерий «визиты И сумма» убран — только сумма трат за **скользящие 30 дней** (колонки
  `required_visits`/`retention_days` дропнуты, `required_spend` → `required_spend_30d`).
- **Повышение — мгновенно**: RPC `loyalty_consume` пересчитывает и кладёт ранг в кэш
  `guest_shop_statuses.current_rank_id` в той же транзакции. **Понижение — read-time**:
  `loyalty_effective_rank_id()` считает ранг по фактическим тратам за 30 дней при чтении,
  без cron и без перезаписи строк (модель сгорания ранга 0012 сохранена, но теперь это единственный механизм).
- Конфигурация остаётся данными (`shop_ranks` + редактор в кабинете кофейни). Схема несёт
  `circuit text not null default 'hall'` и уникальность `(shop_id, circuit, rank_name)` — контур
  «Дом» добавляется отдельной миграцией, UI этапа 1 его не показывает.

**2. Зёрна (новый субмодуль)**

- Таблицы: `beans_ledger` (welcome/earn/redeem, `delta integer`, 1 зерно = 1 ₽) и
  `loyalty_consumptions` (чек: gross, beans_redeemed, card_amount, cash_amount, beans_earned,
  welcome_granted, rank_id, barista_id).
- Начисление: RPC `loyalty_consume` — `round(gross × beans_percent ранга на момент чека)`. Чек
  не кэшбэкает сам себя новым рангом: ставка — effective-ранг ДО проведения чека.
- **Списание с потолком 50% чека** — CHECK `beans_redeemed <= gross_amount / 2` + clamp в RPC.
- **Сгорание 90 дней — read-time**: `loyalty_beans_alive()` считает сумму движений новее
  «последняя покупка − 90 дней»; `loyalty_beans_expire_at()` = последняя покупка + 90 дней.
  Материализованных строк сгорания нет, cron нет.
- Приветственные **300 зёрен** — один раз, автоматически при первом потреблении гостя в кофейне
  (флаг `welcome_granted` в чеке + строка `welcome` в журнале).

**Решение по поведению при нехватке зёрен (выбрано и зафиксировано): списываем доступное, а не отказ.**
Запрос бариста clamp'ится сервером к `min(запрошено, 50% чека, живый баланс)`; чек проводится всегда
(остаток — наличными/картой). То же правило для карты-депозита: карта покрывает min(запрошено, баланс
карты, остаток чека), недостача — живыми деньгами (частичное списание + доплата разрешены брифом).
Отказ с ошибкой только при невалидных вводных: чек ≤ 0, карта не найдена, гость не enthusiast,
у вызывающего нет роли staff этой кофейни.

**3. Потребление в кабинете бариста** (`BaristaLoyaltyPanel`, роут `/dashboard/barista`)

Поток: скан QR (`coffeepassport-guest:{user_id}`, ручной ввод uuid — как было) → контекст гостя
(ранг с цветной меткой и %, траты за 30 дней, живые зёрна с датой сгорания, баланс карты) →
«Продать/пополнить карту» (номиналы 1000/1500/3000/5000, `loyalty_purchase_card`, **не трогает ранг
и зёрна**) или «Провести чек»: сумма → опционально зёрна (≤50%, с подсказкой доступного) →
опционально карта (частично, остаток наличные) → живое превью состава оплаты и кэшбэка →
`loyalty_consume`. Любой исход — потребление: полный gross идёт в прогресс ранга и в базу кэшбэка.

**4. ЛК гостя** (`/loyalty`, «Мои карты»)

Карточка кофейни: ранг с названием и **цветом обжарки** (точка, кэшбэд-бейдж и прогресс-бар красятся
в `color_hex` ранга), значок 🎖 для ордена, прогресс-бар «до статуса X осталось N ₽» по тратам за 30 дней,
**баланс зёрен с таймером обратного отсчёта** до сгорания (предупреждение ≤14 дней), баланс карты,
история операций (чеки, кэшбэк, списания, пополнения, приветственные). Без анонимного тира и без
вкладки «Дом» (один контур).

**5. Орден** (кабинет кофейни, `ShopOrdenForm`)

Ручное назначение ранга гостю по uuid: выбор ранга из лестницы «Зала» + флаг «навсегда» (по умолчанию
включён). RPC `loyalty_assign_orden` — только `cafe_admin` своей кофейни, ранг обязан принадлежать
лестнице hall. Пinned-орден побеждает read-time пересчёт в `loyalty_effective_rank_id()`; `rank_id null`
снимает орден — ранг снова скользит. Зёрна у орденоносца сгорают по общим правилам. В ЛК такой ранг
показывается со значком «🎖 орден».

**6. Кабинет кофейни** (`/dashboard/cafe/loyalty`)

Редактор рангов v2 (название, порядок, цвет, кэшбэк 0–100, порог трат за 30 дней), форма ордена,
реестр «Карты гостей» (одна карта на гостя — полный реестр), журнал чеков со сверкой к Yuma.

## Риски и заметки

- Миграцию 0039 нужно применить на проект (`supabase db push` / SQL Editor) до выкладки кода —
  старые RPC/таблицы удаляются, новых UI без миграции не будет работать (дефенсивные обёртки
  деградируют в пустые состояния, не падая).
- Денежная математика — numeric; зёрна — integer. Округление кэшбэка — `round()` Postgres
  (половина от нечётного уходит вверх) — зафиксировано тестом.
- У ордена с флагом «не навсегда» (pinned=false) effective-ранг уже не скользит? Скользит: pinned=false
  означает «орден без фиксации» — effective-ранг считается по тратам. Семантика не-pinned ордена в этом
  этапе минимальна (присваивает только кэш ранга в момент чека), доводка — под владельца.
- Миграция удаляет `subscriptions`/`loyalty_transactions` безвозвратно — безопасно только потому,
  что база лояльности пустая (бриф). На НЕпустой базе эта миграция неприменима.
- e2e `verify-barista-access` (workflow вручную) обновлён под новую схему, но на живом проде после
  применения 0039 не прогонялся — первый ручной прогон покажет.
