# Product Backlog — Coffee Passport

Generated by `@ideate` (see `.claude/agents.md`). Three trend-grounded feature
proposals for the Enthusiast / coffee-lover persona, prioritized by how
directly they extend the roast-profile/brewing-recipe architecture shipped
in the "Multi-Tier Recipe, Roasting Profile & Extraction Architecture" work
(see `lib/types/coffee.ts` — `BrewingRecipe`, `RoastProfile`).

## 1. Extraction Dial-In Assistant (TDS & Extraction Yield Chart)

**Problem Statement**
`BrewingRecipe` (added in the extraction-architecture work) already captures
`doseG`, `yieldG`, and `waterTds`, but nothing on the Lot Card turns those
numbers into the one chart every serious home brewer now expects: the
classic Coffee Brewing Control Chart (Extraction Yield % × Strength/TDS %,
with the SCA "ideal" balanced-brew box). Right now an enthusiast reading a
Roaster's benchmark recipe sees dose/yield as plain numbers with no sense of
whether it's under-, over-, or correctly extracted — the exact judgment call
trend reports say is now table stakes for engaged home baristas.

**Proposed Feature / UI/UX Design**
- A "Проверить экстракцию" (Check extraction) toggle inside `RecipeCard`
  (`components/coffee/RecipeCard.tsx`) that expands into a small SVG
  scatter chart: x-axis Extraction Yield %, y-axis Strength (TDS%), shaded
  "ideal" quadrant (18–22% EY, 1.15–1.35% strength for filter; separate
  espresso band), with the recipe plotted as a gold dot.
- If the enthusiast has a refractometer, an optional "Мой TDS" input lets
  them plot their own cup against the benchmark's — same comparison instinct
  as the existing `TasteComparison` component (roaster profile vs. guest
  read), just for the numeric brew instead of the flavor axes.
- Copy explaining the two axes in plain language for readers who've never
  seen a brewing control chart before (this app's audience spans total
  beginners to gear-heads — see `DESIGN.md`'s "enthusiast as explorer"
  framing).

**Technical Implementation Plan**
- New pure function `lib/utils/extraction.ts`: `computeExtractionYield({doseG, yieldG, tdsPercent}) → { extractionYieldPercent, strengthPercent }` using the standard `EY% = (yield_g × TDS%) / dose_g` formula — no new dependency, same "pure function, unit-testable" pattern as `lib/utils/roastImport.ts`.
- New `components/coffee/ExtractionChart.tsx` — inline SVG, same no-library
  convention as `RoastCurveChart.tsx`.
- Extend `BrewingRecipe` with an optional `measuredTdsPercent: number | null`
  field (the recipe author's own actual TDS reading, distinct from the
  *target* `waterTds` which is about water treatment, not the resulting
  cup) — additive, so existing localStorage data in `brewingRecipesStore.ts`
  stays valid without a migration.
- No backend change needed — same localStorage-first architecture as the
  rest of the recipe system.

**Target User Persona:** Enthusiast (primary); Roaster/Coffee Shop benefit
secondarily since their benchmark/signature recipes become self-verifying.

## 2. Cross-Grinder Setting Converter

**Problem Statement**
The single biggest gap in the "Адаптировать под себя" flow just shipped
(`components/coffee/EnthusiastRecipeForm.tsx`) is that `grinderSetting` is
free text with no cross-device meaning — a Roaster's benchmark recipe says
"EK43: 850 microns" and the enthusiast has a Comandante C40, with zero
guidance on what number to dial. Trend reports confirm this is now a real
pain point, not a niche one: home brewers are rapidly diversifying into
"lab-level" precision grinders (Comandante, Timemore, 1Zpresso, DF64,
Baratza), so the number of grinder pairs a recipe might need to cross is
large and growing.

**Proposed Feature / UI/UX Design**
- In the adapt-flow modal (`ExtractionTab.tsx`'s "Адаптировать под себя"),
  once the enthusiast picks their own grinder in `ComboSelect`, show a
  "Примерная настройка" (approximate setting) hint computed from a
  conversion table, e.g. *"EK43 @ 850µ ≈ Comandante клик 24–26 (справочно,
  откалибруйте по вкусу)"* — always framed as a starting point, never a
  promise, since burr geometry makes exact conversion impossible.
- A lightweight community layer: after brewing, the enthusiast can confirm
  "у меня получилось похоже при клике 25" — this becomes a second, growing
  data source the estimate blends with over time (start with a static
  reference table, evolve toward crowd-sourced medians).

**Technical Implementation Plan**
- `lib/data/grindReferenceTable.ts` — a static seed table of known
  micron-equivalent ranges per model in `PRO_GRINDER_MODELS` /
  `HOME_GRINDER_MODELS` (`lib/types/coffee.ts`), same seed-array convention
  as `lib/data/roasters.ts`.
- `lib/utils/grindConvert.ts` — pure function
  `estimateGrindSetting(fromModel, fromSetting, toModel) → { estimate: string; confidence: 'reference' | 'community' } | null`, returns `null` (hide the hint) when either grinder isn't in the table rather than guessing.
- New `lib/data/grindConfirmationsStore.ts` (same localStorage pattern as
  `brewingRecipesStore.ts`) to collect the "у меня получилось похоже при…"
  confirmations that later refine the estimate — additive, ships useful even
  before any community data exists.
- Surfaced only in `EnthusiastRecipeForm.tsx`, no schema change to
  `BrewingRecipe` itself.

**Target User Persona:** Enthusiast (primary) — this is the single highest-
leverage fix for the "Adapt to My Setup" flow's biggest friction point.

## 3. Process Passport (Fermentation & Regenerative-Sourcing Transparency)

**Problem Statement**
`Lot.process` (`lib/types/coffee.ts`) is one free-text field ("Washed",
"Natural"...), but transparency reporting for 2026 is explicit that ethical
sourcing and regenerative agriculture disclosure are now a *baseline*
consumer expectation, not a nice-to-have differentiator — and the fastest-
growing part of specialty coffee is exactly the fermentation-forward,
experimental-process lots (anaerobic, co-ferment, thermal shock, extended
fermentation) where a single word like "Natural" hides the interesting part
of the story. This app's whole premise — a passport that reveals the
producer's story once a guest earns it (`FarmerRevealCard`,
`ProducerRoasterCard`) — is the natural home for this.

**Proposed Feature / UI/UX Design**
- A new "Процесс" block on the Lot Card (next to `ProducerRoasterCard`,
  same reveal-gated placement) with structured fields instead of one string:
  process family (Washed/Natural/Honey/Anaerobic/Co-ferment/Other),
  fermentation duration, vessel type (open tank / sealed / GrainPro),
  and an optional roaster-written "почему мы выбрали этот процесс" note.
- A small set of transparency badges (moss-colored, per `DESIGN.md`'s
  quiet-secondary-accent convention — never gold, so it doesn't compete
  with the Q-score seal): "Прямая торговля", "Регенеративное земледелие",
  "Прослеживаемость до фермы" — roaster-asserted, not verified, and
  labeled as such (honest about the trust model, same as this app's
  existing partner-request/RLS trust-model comments).

**Technical Implementation Plan**
- Extend `ProducerProfile` in `lib/types/coffee.ts` with structured
  `processDetail: { family: ProcessFamily; fermentationDays: number | null; vessel: string; roasterNote: string }` and `sustainabilityBadges: SustainabilityBadgeId[]`, both additive/optional so existing seed lots in `lib/data/lots.ts` keep working unchanged.
- `LotBuilderForm.tsx` grows a "Процесс и происхождение" section reusing
  its existing field/label conventions — no new form component needed.
- Read side: a small new `components/coffee/ProcessPassportCard.tsx`,
  same presentational pattern as `ProducerRoasterCard.tsx`.
- No backend change — this rides on the same `lotsStore.ts`
  seed-plus-localStorage-override mechanism as every other Lot field today.

**Target User Persona:** Roaster (author) and Enthusiast (reader) — this is
the one proposal aimed as much at strengthening the Roaster's storytelling
tools as the Enthusiast's discovery experience.

## Sequencing note

Recommended build order: **#2 (Grind Converter)** first — smallest surface
area, directly patches a known gap in code that just shipped. **#1
(Extraction Chart)** second — pure-function + one new SVG component,
similar shape to `RoastCurveChart.tsx` so the pattern is proven. **#3
(Process Passport)** last — touches the Lot schema and `LotBuilderForm`,
the widest blast radius of the three.
