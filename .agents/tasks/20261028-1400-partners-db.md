# 20261028-1400-partners-db

Цель: подключение партнёров через админку пишет в базу. «Активировать партнёра» создаёт строку `coffee_shops` / `roasters`
со статусом и цветом булавки; «Реестр партнёров» читает и меняет базу; карта `/map` для всех посетителей берёт кофейни из базы.
Данные из localStorage не теряются: показываются в реестре и переносятся в базу одной кнопкой.
Автор: Claude (весь код: UI, API, миграция, workflow проверки — по просьбе владельца «UI пишешь ты»). Ревью: Codex `review`.

## План
1. Миграция `0036_partner_directory.sql`: колонки профиля, `status` (`active`/`paused`), цвет с проверкой `#RRGGBB`,
   `partner_request_id`; запись только через сервер (service_role): снять update-политики персонала, revoke insert/update/delete
   у `anon`, `authenticated`. Тест на текст миграции.
2. `lib/data/partnerRows.ts`: строка базы ↔ `CoffeeShop`/`Roaster` (поля null → встроенная карточка → значения по умолчанию),
   проверка ввода, генерация slug.
3. API: `GET/POST /api/admin/partners` (список, активация с привязкой к встроенной карточке, заявка → `activated`),
   `PATCH /api/admin/partners/[kind]/[id]`, `POST /api/admin/partners/import` (перенос из браузера, существующие не перезаписывает),
   `PUT /api/cafe/map-profile` (cafe_id из сессии).
4. Хранилища `coffeeShops.ts` / `roasters.ts`: встроенные ∪ база (база главнее), localStorage больше не смешивается — только
   «данные этого браузера» для переноса. Карта показывает только `active`.
5. UI: модалка активации (привязка к `shop-xo-vsevolozhsk`, точка на карте, ошибки), реестр (статус, бейдж «в базе», перенос),
   профиль на карте кабинета (сохранение в базу + перенос старого профиля из браузера).
6. Workflow `verify-partner-activation`: временные admin и заявка → «Активировать» с цветом и точкой → карта без входа в
   новом контексте показывает булавку этого цвета → уборка заявки, кофейни и учёток.
